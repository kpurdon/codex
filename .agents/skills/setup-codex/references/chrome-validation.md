# Chrome validation

Use this procedure when Chrome control or browser validation is requested. Keep the main checkout as `CODEX_HOME`, even when editing this guidance in a worktree.

## Establish support and ownership

- Consult current official [Browser](https://learn.chatgpt.com/docs/browser) and [Browser extension](https://learn.chatgpt.com/docs/chrome-extension) documentation before installation or repair. At verification on 2026-11-07, Browser documentation excludes CLI/IDE support for the built-in browser; extension documentation describes Chrome control from the ChatGPT desktop app. It does not establish a standalone CLI Chrome-host setup.
- Do not generalize that limitation to all CLI browser control. OpenAI's [MCP guide](https://learn.chatgpt.com/docs/extend/mcp?surface=cli#examples-of-useful-mcp-servers) explicitly lists Chrome DevTools MCP for controlling and inspecting Chrome. Its upstream [Codex configuration](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/client-configurations.md#codex) uses `codex mcp add chrome-devtools -- npx chrome-devtools-mcp@latest`. Check current prerequisites and options before installation; scope the command to the target home.
- Chrome DevTools MCP normally launches Chrome with a dedicated profile. For existing Chrome tabs, its [automatic connection flow](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/advanced-usage.md#automatically-connecting-to-a-running-chrome-instance) uses Chrome 144+, `--autoConnect`, Chrome's remote-debugging settings, and an explicit browser connection prompt. This grants access to the selected profile's open windows; obtain authority for that access and keep actions within the requested tabs. Do not substitute a manually exposed debugging port.
- When the user reports a regression, compare the last working session's tools, launch context, integration version, and config with the current session before concluding that the prior path never worked. A new MCP provider is an integration change, not proof of repairing the previous app connection.
- The documented Chrome route is ChatGPT desktop **Settings > Computer Use > Google Chrome**, the required plugin and ChatGPT extension, and the browser profile containing that extension. Confirm **Manage**, then start a desktop Codex chat with `@Chrome` or an explicit tab mention. Website permission prompts still apply. This is a different runtime from a CLI launch; success there is not CLI acceptance.
- The desktop app owns bundled browser integration and native-host installation. Dotfiles owns executable installation and shell launchers. This repository owns setup guidance and the default config. Preserve unrelated tabs, profiles, credentials, app-managed fields, and local runtime state.

## Diagnose the failed boundary

1. Record the exact tool call, error, time, thread, client/version, `CODEX_HOME`, and default-config versus override state. Use native thread reads when available; label truncated or unavailable historical evidence. Keep API authentication failures separate from browser-host failures.
2. Inspect installed native help, `codex --version`, `codex login status`, `codex plugin list --marketplace openai-bundled --json`, and `codex app-server daemon version`, scoped with `env CODEX_HOME="$target_home"`. `codex doctor --json` can confirm config loading and app/daemon state; it does not prove browser control. Review diagnostics for sensitive data before sharing.
3. Inspect the discovered browser tool's instructions and the installed plugin's troubleshooting documentation. Use only its supported API. Test a dedicated tab on `https://example.com` or an agreed local fixture; do not reuse an incident page or a signed-in production workflow as a probe.
4. Treat `The browser access host is unavailable` as a host-access failure, not proof of a Chrome extension or CDP failure. In bundled integration 26.1103.32239, the browser service emits this error when its access pipe or verification identity is absent, before opening the channel. The CUA launcher requires access verification even when no executor ID was inherited. These are version-specific implementation observations; recheck the installed package when diagnosing another version.
5. For this implementation, the channel inputs are `BROWSER_USE_ACCESS_EXECUTOR_ID`, `BROWSER_USE_ACCESS_PIPE_PATH`, and `BROWSER_USE_ACCESS_VERIFYING_IDENTITY`. Inspect presence only, in the relevant launch context; shell presence alone does not establish what an MCP process inherited. Do not print values, copy them from another process, synthesize them, or disable the verifier. If the host cannot provide the supported channel, report the boundary. Distinguish repairing that connection from adopting a documented MCP integration or moving the task to desktop.
6. If extension/native-host connectivity needs diagnosis, follow the installed browser plugin's `docs/chrome-troubleshooting.md`. In version 26.1103.32239 its read-only checks are the commands below, run from that installed plugin root. Inspect current docs before assuming these paths/options still exist.

```sh
node scripts/chrome-is-running.js --browser chrome --check
node scripts/installed-browsers.js --json
node scripts/check-extension-installed.js --browser chrome --json
node scripts/check-native-host-manifest.js --browser chrome --json
```

An enabled extension and valid manifest establish installation state, not a live host connection or website authorization. Use the owning app's supported repair flow if those checks fail. Follow its permission and restart requirements; do not overwrite native-host files, bypass enterprise policy, restart unrelated sessions, or open an unauthenticated network debugging port. Ordinary tab validation does not justify enabling full CDP access.

## Separate chat handoff from browser connectivity

- A desktop banner saying **This is open in another app** concerns thread ownership. Check which process holds `CODEX_HOME/thread-writer-locks/<thread-id>.lock` with `lsof`, and correlate the desktop log's `thread/resume` failure. A lock file's existence alone does not establish an active owner; do not delete it to force access.
- The CLI daemon and desktop app can use separate app-server processes while sharing saved chats. Opening a chat with the documented [`/app` command](https://learn.chatgpt.com/docs/developer-commands#continue-in-the-desktop-app-with-app) does not establish shared browser authorization. Record the process topology and versions before changing connection settings.
- After the last subscriber disconnects, CLI 0.167.0 defaults to a 60-second idle unload delay; see its [versioned configuration source](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/core/src/config/mod.rs#L4145) and [unsubscribe tests](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/app-server/tests/suite/v2/thread_unsubscribe.rs). Immediate Retry after `/quit` can precede release. Reopening the CLI chat can subscribe again. A timeout is not proof that ownership was released; verify the owner when diagnosing a failed handoff.
- If handoff blocks diagnosis, a separate harmless Chrome probe in a new desktop chat can test the app connection independently. Report desktop success separately from CLI success. Do not stop a shared daemon, copy private host channels, or change internal app switches merely to bypass the failed boundary.

## Prove the requested runtime

- Start a fresh CLI session using the main target home and default config, without adding model, profile, permission, or browser feature overrides. Record the invocation and actual runtime. An inherited reviewer/subagent or a desktop chat is not that proof. A bounded `codex exec --json` probe may retain machine-readable events; inspect `codex exec --help` first.
- Follow the current tool's required initialization. Discover Chrome, create or identify a dedicated test tab, and observe its URL and content. Navigate the same tab to `https://example.org` or exercise a harmless local fixture control; read back the resulting URL/content/state. Capture and inspect a screenshot or short video through the supported browser API. Close only the owned test tab if supported and appropriate.
- Keep the evidence outside tracked runtime/config files. Link the real artifact and exact sources in the handoff and PR; identify local-only links as such. Record capture time, revision, client, steps, expected versus observed result, and limitations. When host access fails before a tab exists, report screenshot/video as unavailable; do not substitute a fabricated demonstration.
- Report separately: plugin installation/enablement, Codex authentication, tool discovery, host connectivity, extension/native-host status, website permission, tab creation, navigation/control, readback, and visual evidence. If a required step fails, Chrome readiness remains blocked even if a documentation fix is delivered.
